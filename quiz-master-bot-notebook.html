CONCEPT 1 / DATA STRUCTURES

Lists

A list is an ordered box of items you can look up by position, add to, and measure.

Think of a list as a numbered coat rack: each hook has a fixed position starting at 0, and you can always ask "what's on hook 2?" or hang up one more coat at the end.

WHY IT MATTERS

Every question in the quiz app lives inside a list — QUIZ_BANK["Maths"] is a list of questions. Without lists, you'd need a separate variable for every single question, which doesn't scale past three or four.

TRY IT

fruits = ["apple", "banana", "cherry"]len = 3
 

CODE, FROM day.py

day.py
fruits = ["apple", "banana", "cherry"]
print(fruits[0])          # apple — indexing starts at 0
fruits.append("orange")  # adds to the end
print(len(fruits))       # 4
PITFALL Asking for fruits[3] before appending will crash with IndexError — the list only has indices 0, 1, 2. Always check len(fruits) if you're not sure a position exists.
CONCEPT 2 / DATA STRUCTURES

Dictionaries as records

A dictionary pairs a name (key) with a value, so you look things up by meaning instead of position.

It's a phone book: you don't remember your friend's number by "the fifth entry," you look them up by name. capital["France"] reads exactly like that lookup.

WHY IT MATTERS

A single quiz question is naturally a record, not a list: {"question": "...", "answer": "..."}. Using a dict means the code always asks for item["question"] by name — clear, and impossible to mix up with the answer by accident.

TRY IT

capital = {"France": "Paris", "Japan": "Tokyo"}
Click a key on the left to look up its value →

CODE, FROM day.py

day.py
capital = {"France": "Paris", "Japan": "Tokyo"}
print(capital["France"])  # Paris — lookup by key, not position
PRO TIP Looking up a missing key (capital["Spain"]) raises KeyError. The safe version is capital.get("Spain", "unknown"), which returns a fallback instead of crashing.
CONCEPT 3 / DATA STRUCTURES

A list of dictionaries is a table

Put several records in a list and you get exactly the shape of a spreadsheet: each row is a dict, each column is a key.

One dict is a single index card. A list of them is the whole card box — flip through it, and every card has the same two fields: question and answer.

WHY IT MATTERS

This is the exact shape QUIZ_BANK["Maths"] uses in the real app: a list of eight dicts, each with a "question" and "answer" key. Zoom out from one record and you get the whole quiz bank.

CONCEPT 4 / LOGIC

The quiz loop

A for loop walks through the list one record at a time, comparing the player's answer to the stored one.

It's the same motion as marking a stack of quizzes by hand: pick up the next paper, read the answer key, mark it right or wrong, move to the next one.

THE LOGIC, STEP BY STEP

CODE, FROM day.py

day.py
for item in questions:
    user_answer = input(item["question"] + " ")
    if user_answer == item["answer"]:
        print("Correct!")
    else:
        print("Wrong. The answer was", item["answer"])
PRO TIP In quiz.py this same comparison is done case-insensitively with ans_input.lower() == current_q["answer"].lower(), so typing "tokyo" still counts as correct.
CONCEPT 5 / APP STATE

Streamlit session state

Every click on a Streamlit app re-runs the entire script from top to bottom — so a normal variable resets to its starting value every time. st.session_state is the one thing that survives a rerun.

Imagine a whiteboard that gets wiped clean after every meeting, except for one sticky note in the corner marked "keep." Ordinary variables are the whiteboard; session state is the sticky note.

CODE, FROM quiz.py

quiz.py
if "score" not in st.session_state:
    st.session_state.score = 0   # only runs once, ever

# later, inside a button click:
st.session_state.score += 1
st.rerun()  # script restarts, but session_state.score keeps its value
PITFALL st.session_state.score = 0 written outside an if "score" not in st.session_state: guard would reset the score to zero on every single rerun — including the one triggered by the player's own click.
CONCEPT 6 / APP STATE

The state-machine pattern

The whole app is one variable, game_stage, that's always exactly one of three values — and an if / elif / elif chain decides which screen to draw based on it.

It's a traffic light: only one color is ever on, and that one color determines what everyone on the road is allowed to do next.

CODE, FROM quiz.py

quiz.py
if st.session_state.game_stage == "START":
    # show the name + category form
elif st.session_state.game_stage == "QUIZ":
    # show the current question
elif st.session_state.game_stage == "RESULTS":
    # show the final score and rank
PRO TIP Because only one branch of the if/elif chain ever runs, the three screens can never overlap or show at the same time — the stage variable is the single source of truth.
CONCEPT 7 / LOGIC

Shuffling without breaking the original

random.shuffle() reorders a list in place — so the app always shuffles a copy of the question bank, never the original.

Think of the original quiz bank as a master answer key locked in a drawer. You photocopy it, shuffle the photocopy on your desk, and the master stays in order for the next player.

TRY IT

mode: safe (.copy() first)
QUIZ_BANK["Maths"] (original)
questions (working copy)
 

CODE, FROM quiz.py

quiz.py
questions = QUIZ_BANK[category].copy()  # copy first!
random.shuffle(questions)             # shuffles the copy only
st.session_state.questions = questions
PITFALL Drop the .copy() and random.shuffle(QUIZ_BANK[category]) shuffles the master bank itself — every future player then gets a permanently reordered question set, and repeated plays slowly scramble your source data.
CONCEPT 8 / LOGIC

Turning a percentage into a rank

A chain of if / elif comparisons converts a single number — percentage correct — into a badge the player can be proud of (or motivated by).

It's exactly like exam grade boundaries: 90 and above is an A, 80 and above a B — the same idea, just with quiz-master badges instead of letters.

TRY IT

percentage75%
🥇 Quiz Expert

CODE, FROM quiz.py

quiz.py
def get_rank(percentage):
    if percentage == 100:
        return "🏆 Grandmaster"
    elif percentage >= 75:
        return "🥇 Quiz Expert"
    elif percentage >= 50:
        return "🥈 Knowledge Seeker"
    else:
        return "🥉 Rookie"
PRO TIP Order matters here: because 100 is checked first, a perfect score never falls through to the >= 75 branch. Reordering these checks would quietly change who gets Grandmaster.
CONCEPT 9 / PERSISTENCE

Saving scores to a file

Opening a file in "a" (append) mode adds a new line without touching what's already there; "w" (write/overwrite) mode erases the file first.

Append mode is a guestbook — every visitor adds a line, nobody erases the ones before. Overwrite mode is a whiteboard — writing on it wipes whatever was there.

TRY IT

scores.txt
alex | Maths | 8/8 | Rank: 🏆 Grandmaster
 

CODE, FROM quiz.py

quiz.py
def save_score(player_name, score, total, category, rank):
    with open(FILE_NAME, "a", encoding="utf-8") as file:
        file.write(f"{player_name} | {category} | {score}/{total} | Rank: {rank}\n")
PITFALL If save_score used "w" instead of "a", every new player would erase the entire leaderboard and leave only their own score — that's exactly what turns a guestbook into a whiteboard by accident.
CONCEPT 10 / PERSISTENCE

Parsing saved lines back into data

A plain text file only stores characters — .split(" | ") turns a line back into separate fields, and a length check filters out lines that don't fit the expected shape.

TRY IT — EDIT THE LINE

CODE, FROM quiz.py

quiz.py
parsed_data = [s.split(" | ") for s in scores
               if len(s.split(" | ")) == 4]  # drop malformed lines
PRO TIP This is exactly why scores.txt's stray lines like "Sam scored 3" and "A new scored line" never crash the sidebar — they don't split into 4 pieces, so the guard silently skips them instead of raising an error.

Key takeaways

  • Data shape drives everything. A list of dictionaries is what lets one for loop handle any number of questions, in any category, without special-casing.
  • State needs a home. Streamlit reruns the whole script on every interaction — session_state is what lets the app remember the score, the stage, and the current question across those reruns.
  • One variable, one truth. The game_stage pattern keeps the START/QUIZ/RESULTS screens from ever overlapping or getting out of sync.
  • Files are just text. Saving is one formatted line appended per player; loading is splitting those lines back apart and defensively skipping anything malformed.
What this unlocks next: the same three patterns — structured data, a state machine, and simple file persistence — are the backbone of almost every small interactive tool you'll build next, from a to-do app to a full multi-user game. You already know them.
