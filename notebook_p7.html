THE LANDSCAPE

Twelve ideas, four families

Click any node to jump straight to that section. Representing data turns films into numbers, similarity math compares those numbers, ranking & filtering narrows the results, and display turns numbers back into something readable.

CONCEPT 1 / REPRESENTING DATA

Films as genre vectors

Every film is stored as a list of six numbers — one strength rating (0–5) per genre. That list of numbers is the film, as far as the math is concerned.

It's like a flavor profile on a hot-sauce label: instead of describing a sauce in words, you rate it 0–5 on heat, tang, sweetness and smokiness — two sauces with similar numbers will taste similar, even before you open the bottle.

WHY IT MATTERS

This is a simplified, human-readable stand-in for what a real embedding model produces: instead of six hand-picked genre scores, a language or vision model outputs hundreds of learned numbers — but the underlying idea, "meaning as a vector," is identical.

CONCEPT 2 / SIMILARITY MATH

A vector is a point in space

With just two genre dimensions, a film's vector is literally a point you can plot on a graph — an arrow from the origin to that point. More genres just means more dimensions than we can draw, but the idea doesn't change.

Think of a treasure map: "5 steps east, 2 steps north" describes one exact spot. A genre vector is the same kind of instruction, just with genre-axes instead of compass directions.

CONCEPT 3 / SIMILARITY MATH

Cosine similarity — angle, not distance

Cosine similarity measures the angle between two vectors. Two vectors pointing the same direction score close to 1, regardless of how long either one is.

Picture two flashlights: if they point the exact same way, their beams overlap completely — it doesn't matter if one is a keychain light and the other a searchlight. Cosine similarity only cares about the direction they're aimed.

TRY IT — DRAG EITHER ARROW

cos(θ) = dot(u,v) / (‖u‖ · ‖v‖)

CODE, FROM app_p7.py

app_p7.py
def cosine_similarity(u, v):
    dot = np.dot(u, v)
    norm_u = np.linalg.norm(u)
    norm_v = np.linalg.norm(v)
    if norm_u == 0 or norm_v == 0:
        return 0.0
    return dot / (norm_u * norm_v)
PITFALL Skip the zero-norm check and a film with an all-zero vector (or comparing a vector to itself as all zeros) would divide by zero and crash. The guard returns a neutral 0.0 instead.
CONCEPT 4 / SIMILARITY MATH

Dot product — direction and magnitude

The dot product is the raw ingredient cosine similarity is built from — but used alone, it rewards longer vectors too, not just well-aligned ones.

Same two flashlights, aimed the same way: a searchlight and a keychain light have identical direction (identical cosine similarity), but the searchlight's raw dot product is much bigger simply because it's more powerful.

TRY IT — SCALE VECTOR B'S LENGTH

direction fixed — only magnitude changes

CODE, FROM app_p7.py

app_p7.py
def dot_product(u, v):
    return float(np.dot(u, v))
PRO TIP Notice: as you drag the slider, cosine similarity barely moves but the dot product changes a lot. That's exactly why app_p7.py ranks by cosine similarity by default — it's a fairer comparison between a "small" film and a "big" one.
CONCEPT 5 / SIMILARITY MATH

Euclidean distance — the straight-line gap

Euclidean distance measures the literal, ruler-straight gap between two vector tips. Lower means closer — it's the only one of the three metrics where "lower is better."

It's the difference between "these two people are walking the same direction" (cosine) and "these two people are standing right next to each other" (Euclidean) — related ideas, but not the same question.

TRY IT — DRAG EITHER ARROW

distance = ‖u − v‖

CODE, FROM app_p7.py

app_p7.py
def euclidean_distance(u, v):
    return float(np.linalg.norm(u - v))
PITFALL Try dragging vector B far along the exact same line as vector A (same direction, very different length) — cosine similarity stays near 1, but Euclidean distance grows. The two metrics can disagree about which film counts as "similar."
CONCEPT 6 / RANKING & FILTERING

Filtering before you rank

The sidebar's language checkboxes shrink the candidate pool before any similarity math runs — so a Telugu fan can exclude Tamil and Kannada films from ever appearing in the results.

TRY IT

CODE, FROM app_p7.py

for title, info in CATALOG.items():

        continue

PRO TIP Filtering first, not after, matters for performance at scale: with a catalog of 40 it's invisible, but with 40 million items you'd never want to compute similarity for candidates you're about to throw away anyway.
CONCEPT 7 / RANKING & FILTERING

Sorting by similarity, then slicing top-N

Once every candidate has a cosine similarity score, sorting descending puts the best matches first — and Python's list slicing [:top_n] keeps only as many as the user asked for.

TRY IT

results.sort(key=..., reverse=True)[:top_n]

CODE, FROM app_p7.py

app_p7.py
results.sort(key=lambda r: r["cosine_similarity"], reverse=True)
top_results = results[:top_n]
PRO TIP key=lambda r: r["cosine_similarity"] tells Python exactly which field to sort by inside each dict — without it, Python has no way to compare two dictionaries to decide which comes "first."
CONCEPT 8 / RANKING & FILTERING

Clamping negative similarity for display

Cosine similarity can mathematically go negative (opposite-pointing vectors) — but a progress bar can't show a negative percentage, so the display layer clamps it to zero without changing the underlying number used for ranking.

TRY IT

similarity_percent = max(0, cos_sim) * 100
displayed: 65.0%

CODE, FROM app_p7.py

app_p7.py
similarity_percent = max(0, r["cosine_similarity"]) * 100
st.progress(similarity_percent / 100)
PITFALL The clamp only affects what's displayed. Sorting still uses the true, unclamped cosine_similarity — so a film with -0.2 similarity correctly ranks below one with 0.1, even though both would show as 0% and 10% respectively.

Key takeaways

  • Meaning becomes numbers. Turning a film into a vector is what makes "similarity" computable at all — this is the same move a real embedding model makes, just with human-picked numbers instead of learned ones.
  • Direction vs. distance are different questions. Cosine similarity, dot product, and Euclidean distance can each rank the same catalog differently — knowing which one you're using matters.
  • Filter first, rank second. Narrowing candidates before running the math keeps the app fast and the results relevant.
  • Display logic isn't ranking logic. Clamping a negative similarity to 0% for a progress bar never touches the real number used to sort the results.
What this unlocks next: swap the hand-typed genre vectors for real embeddings from a language model, and this exact cosine-similarity code becomes the retrieval step of a RAG system — the same math, just with smarter numbers underneath.
