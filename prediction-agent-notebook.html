01 / 07

The linear model

Every prediction the app makes comes from one formula:

predict(x, m, c)
score = m × hours + c

m is the slope — how many extra marks one more hour of study is worth. c is the intercept — the score the line predicts at zero hours. Training the model means nothing more than searching for the m and c that make this line sit as close as possible to the real data.

Real-life analogy — think of a ruler laid across a scatter of dots on graph paper. Tilting the ruler changes m; sliding it up or down changes c. Nobody hands you the right position — you have to find it by trial and adjustment, which is exactly what the training loop automates.

Why it matters

Linear regression is the simplest possible predictive model, and it's the ancestor of everything more complex: logistic regression, neural network layers, and even large language models all still contain a weight × input + bias step at their core. Understanding this line means you already understand the shape of the bigger equations.

# PREDICTION
def predict(x, m, c):

That's the entire prediction step. Everything else in the project exists to find good values of m and c to hand this function.

PITFALL

It's tempting to think a "smarter" model needs a fancier formula. Here, the formula never changes — only m and c do. Most of the intelligence in a learning system lives in the search for parameters, not in the prediction formula itself.

02 / 07

The loss function — Mean Squared Error

To know whether a line is good, you need a single number that says "how wrong is this line, overall?" That number is the loss. This project uses Mean Squared Error: for every point, measure how far off the prediction is, square that error, then average the squares.

Real-life analogy — imagine five archers shooting at a target, and you want one score for the whole team. Squaring each miss before averaging punishes wild misses far more than near-hits — one arrow that's way off the mark hurts the team score more than five arrows that are each a little off. That's exactly why gradient descent, guided by this loss, works so hard to eliminate large errors first.

Why it matters

Squaring does two jobs at once: it makes every error positive (so a +5 error and a −5 error don't cancel out), and it makes big errors count disproportionately more, which gives the training loop a clear signal about which mistakes to fix first.

app.py
# LOSS
def calculate_loss(m, c):
    total = 0
    for x, real in zip(hours, scores):
        prediction = predict(x, m, c)
        error = prediction - real
        total += error ** 2
    return total / len(hours)
PRO TIP

Lower loss always means a better fit to the training data — but a loss of exactly 0 usually means the model has memorised the five points rather than learned the underlying trend. With only five points here that's mostly a curiosity, but on real projects it's the seed of overfitting.

03 / 07

Gradients — which way to nudge

Loss tells you how wrong the line is. A gradient tells you which direction to move m and c to make it less wrong. Concretely, the gradient is the slope of the loss itself — if you nudged m up slightly, would the loss go up or down, and by how much?

Real-life analogy — picture standing on a hillside in thick fog, trying to reach the valley floor. You can't see the whole landscape, but you can feel which way the ground slopes under your feet right now. The gradient is that feeling — a local reading of "downhill" that's enough to take one safe step at a time.

The logic — step through it
1For every point, find the current error

error = predict(x, m, c) − real. This is the same error used for the loss, before it gets squared.

2Weight the error by how it entered the prediction

m was multiplied by x, so its gradient scales the error by x: grad_m += 2 · error · x. c was just added, so its gradient is the error alone: grad_c += 2 · error.

3Average across all points

Divide both totals by the number of points, so the step size doesn't depend on how much data you have.

4Step in the opposite direction

A positive gradient means "increasing this parameter increases the loss" — so you move the parameter the other way: m = m − learning_rate × grad_m.

# GRADIENTS
def calculate_gradients(m, c):
    grad_m = 0
    grad_c = 0
    n = len(hours)
    for x, real in zip(hours, scores):
        prediction = predict(x, m, c)
        error = prediction - real
        grad_m += 2 * error * x
        grad_c += 2 * error
    return grad_m / n, grad_c / n
PITFALL

It's easy to misremember the sign and add the gradient instead of subtracting it — which sends the line uphill, making the loss worse every step. If your loss ever climbs during training, this is the first thing to check.

04 / 07

Gradient descent — the training loop

Gradient descent is simply: compute the gradient, take a small step against it, and repeat, over and over, until the line stops improving by much. Each repetition is one training "step."

Real-life analogy — it's the same foggy hillside from section 3, but now you actually walk. Feel the slope, take one small step downhill, feel the new slope, take another step. A thousand small steps, each individually modest, add up to a walk all the way down to the valley.

Worked code example
app.py
# TRAIN MODEL
def train_model(learning_rate, steps):
    m, c = 0, 0
    history = []
    for step in range(steps):
        gm, gc = calculate_gradients(m, c)
        m = m - learning_rate * gm
        c = c - learning_rate * gc
        history.append(calculate_loss(m, c))
    return m, c, history

This is exactly the loop this widget is animating — m and c both start at zero and walk toward the values that best fit the five data points.

PRO TIP

Storing history at every step, like app.py does, costs almost nothing and gives you a free debugging tool: plot it, and a healthy training run looks like a smooth downward curve that flattens out — exactly what you should see in the chart above.

05 / 07

Learning rate & steps

The learning rate controls how big each step downhill is. Too small, and training crawls. Too large, and each step can overshoot the valley floor and land higher up the other side — sometimes worse than where it started.

Real-life analogy — back on the hillside: tiny, cautious steps get you down safely but slowly. Confident strides get you there fast — but take a stride too large on a steep slope and you can stumble straight past the valley and end up higher than when you started.

06 / 07

Streamlit & session state

Training math is only half the project — the other half is turning it into an app someone can actually click through. app.py organises this into three tabs, and uses st.session_state as memory that survives between them.

Real-life analogy — Streamlit reruns your entire script from top to bottom on every click, like restarting a play from scene one each time the audience claps. session_state is the one prop the actors are allowed to carry with them between restarts — without it, the model you trained in the Train tab would be forgotten the instant you opened Predict.

The logic — step through the app
Press play to watch a click travel through the app.
Worked code example
app.py — inside the Train tab
if st.button("🚀 Train Model", type="primary"):
    m, c, history = train_model(learning_rate, int(steps))
    st.session_state.m = m
    st.session_state.c = c
    st.session_state.history = history

The Predict tab later checks if "m" not in st.session_state and shows a warning if training hasn't happened yet — session state is also how the app knows what stage the user is at.

PRO TIP

Any variable a Streamlit app needs to remember across reruns — not just across tabs — belongs in session_state. A plain local variable is wiped the moment the script reruns.

PITFALL

The slider above goes well past 5 hours — the largest value the model was actually trained on. Far outside the training range, a straight line keeps climbing forever, which is rarely realistic (a student studying 40 hours a week won't keep gaining marks at the same steady rate). This is extrapolation risk, and it applies to every linear model, not just this one.

Key takeaways

What you now understand

You've seen every moving part behind app.py: a formula that predicts, a loss that scores the prediction, a gradient that points toward improvement, a loop that takes that step thousands of times, a learning rate that controls how boldly it steps, and a small Streamlit app that wires all of it into something clickable.

Nothing here was a black box — you built the descent, the loss, and the gradients yourself, in plain Python, the same way libraries like scikit-learn or PyTorch do it under the hood at far larger scale. A neural network is, at its core, many of these m·x + c steps stacked and connected — the training loop you just watched converge is the same loop that trains them, just repeated across millions of parameters instead of two.

Next, try swapping in a second input feature (say, hours slept), or a dataset with more than five points, and watch the same four functions — predict, calculate_loss, calculate_gradients, train_model — barely need to change to handle it. That's the real payoff of building it from scratch once: you'll recognise this shape everywhere you go next.
